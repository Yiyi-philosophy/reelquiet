## 奖励联动设计（草案，待确认）

### 原则
1. **零 token**：只观察已经在发生的事件，绝不调用 `$.model`。
2. **奖励里程碑，不奖励过程量**：奖励"红转绿"、"提交了"、"任务完成了"，不奖励"改了多少行"、"跑了多少次测试"，否则可以刷。
3. **信号给道具，不直接给鱼**：进度信号产出**鱼饵 / 道具**，作用于后续的抛竿。运气仍然是核心乐趣，进度只用来改变概率。
4. **边际递减 + 每日上限**：防止用 `git commit --allow-empty` 这类方式刷。
5. **权限面最小**：优先只用事件观察和 `$.fs.read`，避免 `$.process` 和 `$.http`。

### 候选信号

| 信号 | 获取方式（零 token） | 防刷 | 建议奖励 |
|---|---|---|---|
| **等待时长**（耐心） | `turn.start` → `turn.complete` 的 `durationMs` | 天然难刷 | 时间越长，越容易进入深水区、钓到大鱼 |
| **任务完成** | `turn.complete` 且 `isAborted: false`；`classic.TaskCompleted`（Claude 自己的任务清单项完成） | 每个 turn 最多计一次 | 普通鱼饵 |
| **测试红转绿** | `tool.call` 匹配 Bash 的测试命令，同一会话内先失败后成功 | 只奖励"转绿"这个瞬间，一直绿不重复奖励 | 金色鱼饵（稀有鱼概率提升） |
| **Git 提交** | 方案 A：观察 Claude 执行的 `git commit` 成功；方案 B：用 `$.fs.read` 读 `.git/logs/HEAD`（reflog），用户手动提交也能统计，且不需要 `process` 权限 | 空提交 / 极小提交递减；每日上限 | 宝箱（解锁装饰、新钓点） |
| **创建 PR** | 观察 `gh pr create` 成功 | 每个分支一次 | 稀有宝箱 |
| **缓存命中率高** | `turn.step` 结果中的 `cache_read_input_tokens` 占比 | 只是状态，不累积 | 环境效果："鱼群聚集"（咬钩更快） |
| **环境生态** | 时间、仓库语言（文件后缀）、`$.session.repo()` | 不影响稀有度 | 决定出现哪些鱼种 |

### 明确不做（v1）
- **PR 被合并**：需要 `gh` 或网络请求，涉及认证、慢、扩大权限面。留到 v2，作为可选项。
- **代码行数 / diff 大小**：会奖励"多改"，和"好习惯"相反。
- **任何基于模型判断的"代码质量评分"**：违反零 token 原则。
